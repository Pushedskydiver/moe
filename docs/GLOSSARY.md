# Glossary

Ubiquitous language for moe — use consistently in code, docs, commits, and persona prompts.

Each entry gives the term's current meaning. A chunk id in an entry (e.g. `3.4c`) points to that chunk's build history: its `## <id>` section in `docs/history/BUILD-NARRATIVE.md` once the chunk is finished (5.3's per-persona sub-chunks, 5.3a–5.3h, share §5.3; 5.3a-ii has its own section), its `BUILD_PLAN.md` entry until then. A fix made outside `BUILD_PLAN.md` cites the PR that landed it instead. The fuller entries this doc carried until 2026-09-27 are at `git show 1b3c4f0:docs/GLOSSARY.md`.

`docs/VISION.md` Appendix B lists several terms as "carried forward unchanged from the previous design's glossary." That prior design "is not retained in this repo as a checkable reference file" (`docs/VISION.md`'s own front matter) — the entries below define those terms from where moe's own current docs actually use them, or from their standard industry meaning where moe hasn't specified anything narrower yet. Where a term is still an open question rather than a settled definition, the entry says so.

## Anti-fabrication (VISION §7.6)

- **Execution hallucination** — An agent claiming to have completed a sub-stage of work it did not actually complete. The academic name for the second of moe v3's three named failure modes (`docs/VISION.md` §0).
- **Evidence-gated claim** — A status statement a persona is structurally prevented from emitting unless it's backed by a real `toolCallId`/`toolOutputSnippet` pair.
- **Ungrounded fabrication** — A claim with no tool-call evidence at all — closed by the evidence-gated-claim schema itself.
- **Misgrounded fabrication** — A claim backed by real but irrelevant evidence. Closed only for Tier 2/3 claims (see Autonomy & trust, below), by independent verification — the schema gate alone doesn't catch it.

## Autonomy & trust (VISION §8)

- **Risk tier** — The path × change-shape classifier that gates how much review a change needs before merge (`docs/VISION.md` §8.1) — replaces the old time-gated Probation model entirely.
- **Tier 0** — Auto-merge immediately. All CI green; no sensitive path touched; diff below a size threshold; docs/config/lint-only or a non-major devDependency bump.
- **Tier 1** — Fast single-approve, same-day. Logic change with an accompanying test, in a path the agent has a track record on.
- **Tier 2** — Standard review. Any logic change without an accompanying test, a path with no track record, or a diff crossing package boundaries.
- **Tier 3** — Mandatory named-owner review, cannot be satisfied by the requesting persona or the human who dispatched it. Auth, payments, PII/secrets, CI/CD config, migrations, or any destructive operation, regardless of track record — a hard floor autonomy doesn't earn past.
- **Track record** — A path's history of unreverted merges; shifts a change down at most one tier, and never into Tier 3. A diff spanning multiple directories takes the _minimum_ track record across them; a directory rename/move preserves it when git detects the rename; a brand-new directory never inherits it (Tier 2 floor); the threshold is **N = 5** consecutive unreverted merges (`docs/decisions/TRACK-RECORD-DEFINITION.md`, resolving `docs/VISION.md` §8.1).
- **Trust Level** — The previous design's time-gated Probation → Trusted → Veteran ladder. **Superseded** by the risk-tier model above — there is no more Probation phase gating all pulls.
- **Veto signal** — Alex's 🛑 reaction, which holds a merge. Carries over conceptually from the previous design (`docs/VISION.md` §8.2); not yet built.

## Team & ceremonies (VISION §3, §6)

- **ScrumBan** — Moe's process model: Kanban flow (continuous pull, WIP limits) plus Scrum-style ceremonies layered on top (`docs/VISION.md` §3.1).
- **Ceremony** — A structured, scheduled team ritual (e.g. weekly replenishment, monthly review) — `docs/VISION.md` §3.2; specific ceremony formats live in `docs/CEREMONIES.md` once written (do-not-touch surface, `AGENTS.md`).
- **Brief** — A work-scoping artifact a persona produces before implementation (illustrated in `docs/VISION.md` §1.3's day-in-the-life dialogue: "Sarah's brief for the packages issue"). `composeBrief` (`packages/agents`) produces a `{summary, scope}` framing-plus-itemized-list output — no `title`, since the ticket's own title already exists by the time this call runs — posted as a plain Slack message to `#moe-team` (`TEAM_CHANNEL_ID`). A `ticket_briefs` row (`{ticketId, channelId, messageTs, summary, scope}`) is persisted for idempotency and for a reaction handler to find the message and drive the reaction-triggered `Brief`→`Plan` transition — see **Confirming question (Mid-band)**'s own entry below for how the reaction is disambiguated. The Brief-stage pull-loop work step (`apps/server`'s `handleBriefStageTicket`) checks that row first, before any LLM call — a ticket already briefed is skipped, never re-posted. (6.1b; widened to carry content 6.1c; reaction-triggered transition 6.1d.)
- **Plan** — A concrete-approach artifact Marcus produces once a ticket has a Brief (`docs/VISION.md` §1.3/§3.3 name the lifecycle stage — "Marcus is picking up the plan", "Sarah triages → Marcus plans → Riley builds" — but unlike Brief, VISION never shows a plan's own content the way it shows Sarah's brief). `composePlan` (`packages/agents`) directly operationalizes Marcus's own shipped `prompt.md` ("what the approach is, what you're confident about, what you're not, and what alternatives you considered for anything substantial"), producing a `{approach, confidence, alternativesConsidered[], openQuestions[]}` structured-judgment output — no `title`, same reasoning as Brief's own omission — grounded in the ticket's already-persisted Brief content (`briefSummary`/`briefScope`, not a fresh GitHub-issue-body fetch, since Marcus's own prompt has no live-codebase-read tool), posted as a plain Slack message to `#moe-team` (`TEAM_CHANNEL_ID`). A `ticket_plans` pointer (`packages/core`, `{ticketId, channelId, messageTs}` — deliberately pointer-only, since nothing downstream of a Plan reads its content back yet) is persisted for idempotency, and doubles as the row a reaction handler uses to find the message and drive the reaction-triggered `Plan`→`Build` transition (`dispatchPlanApproval`, `apps/server`'s `handle-reaction-added.ts`) — the last forward-approval reaction-triggered stage transition in the lifecycle (Build→Review is a PR open, not a reaction; Review→Done is the merge-action executors). See **Confirming question (Mid-band)**'s own entry below for how the three-way `thumbsup` collision is disambiguated. The Plan-stage pull-loop work step (`apps/server`'s `handlePlanStageTicket`) checks that pointer first, before any brief lookup, cost-cap read, or LLM call — a ticket already planned is skipped, never re-posted; a ticket with no usable Brief yet is skipped too (logged, not posted), which also excludes it from the pull loop's `needsWork` candidacy (`createPlanStageNeedsWorkCheck`) so it can never starve a genuinely plannable newer ticket. (6.1c; reaction-triggered transition 6.1e.)
- **EOD digest** — The end-of-day summary a persona posts to the team channel (`docs/VISION.md` §6.5), standing in for a standup — Alex is continuously present in the channel, so a bolted-on standup on top would be redundant (§3.2).
- **Core hours** — The window during which proactive persona behavior (sends, intake drafts) is allowed; off-hours it is **not performed**. Nothing defers: nothing re-attempts an off-hours intake draft or question later; real deferral is 3.9's step (2), still unbuilt. A blocked _ambient_ High- or Mid-band intake writes a `review_queue` row instead of vanishing, which preserves the message without performing the action (3.9). Settled at 2.7a (Alex confirmed, not inferred): 08:30–17:00 Europe/London Mon–Fri, weekends and GOV.UK bank holidays (england-and-wales division, cached with a serve-stale-on-failure fallback) excluded. Reactive behaviour is exempt — a DM reply (2.7a), a reaction-outcome dispatch (3.4a-iii/3.4b-ii), and a DM-triggered intake draft or confirming question (3.7) each respond to a human action rather than Moe acting unprompted, so §14's rest rule doesn't reach them. The exemption covers **rest only** — the per-persona cost cap still applies to every billed call on those paths. `docs/VISION.md` §6.4 delegates the parameters here.
- **Away-detection** — Reading Alex's Slack status text/emoji against a keyword list to suppress off-hours proactive behavior further. Settled at 2.7b (Alex confirmed, not inferred): text keywords `away`/`holiday`/`OOO` (whole-word, case-insensitive — a bare substring match would false-positive inside `giveaway`/`runaway`); emoji shortcodes `palm_tree`/`beach_with_umbrella`/`airplane`/`face_with_thermometer`/`thermometer`/`hospital` (verified against the real `iamcal/emoji-data` short-name database — `beach_with_umbrella` specifically, not the more obvious-sounding `beach_umbrella`). Deliberately excludes momentary-busy signals (🔴 do-not-disturb, 🏠 WFH) that don't reliably mean extended absence. First real consumer is 7.2b; `isAway`/`fetchSlackStatus` (`packages/slack`) are reusable primitives only so far.
- **Classes of Service** — A Kanban capacity concept (work-item categories with different WIP/priority treatment). **Resolved** at 4.3 (`docs/decisions/BOARD-AND-CAPACITY-MODEL.md`): two classes, **Standard** and **Expedite** — Expedite for `#moe-incidents`-sourced work or `severity: 'Critical'`, jumping ahead of Standard work within its board status. Tracked via a `classOfService` ticket-schema field (not derived from `severity`, since the two are independent axes; 4.5). **Assignment** (`classifyClassOfService`, wired into `reaction-outcome-actions.ts`'s `commitAsTicket`) and queue-jump **ordering** (`findNextClaimableTicket`, consulted by the pull loop before a claim) are both live (6.1a-i).
- **WIP limit** — The per-board-status cap that gives "capacity" an actual ceiling to pull against (`docs/VISION.md` §3.1). **Resolved** at 4.3 (`docs/decisions/BOARD-AND-CAPACITY-MODEL.md`): Brief 3, Plan 2, Build 2, Review 2 — Backlog/Done/Cancelled uncapped — small starting numbers set without real throughput data (same reasoning as the track-record N=5 threshold), revisable once real pull/throughput data accumulates (the trigger's other condition, personas beyond Sarah, is already met). `evaluateWipLimit` is the guard function, wired in as the WIP-gate check inside `transitionTicketStatus` (4.5; wired 6.1a-ii).
- **WSJF** — Weighted Shortest Job First — a prioritization technique (cost of delay ÷ job size). Named in VISION Appendix B as carried-forward vocabulary; not yet wired into any moe mechanism.

## Intake & triage (VISION §5)

- **Stage 0 — channel scoping** — The coarse, per-surface filter that runs before the classifier ever sees a message (`docs/VISION.md` §5.2) — "a message only enters the pipeline if it's in a channel/DM the team already treats as work-relevant." Built as `isSurfaceInScope`/`ChannelScopeConfig` (`packages/core`; 3.2): a DM to a named persona is always in scope (§5.3 — handled by that persona's own app without Sarah in the loop); a channel is in scope only if its ID is in the configured work-relevant set (§6.1's roster: `#moe-team`/`#moe-incidents`/`#moe-research` in, `#moe-random` out). Coarse by design — it removes whole channels of banter without keyword rules, leaving message-level precision to Stage 1. Wired into `apps/server`'s inbound-message handler (`parseChannelScopeConfig`, `packages/agents`, resolves real Slack channel IDs from `MOE_WORK_RELEVANT_CHANNEL_IDS`; 3.3) — for the `channel` arm only; the `dm` arm is reachable via 3.7's DM cascade entry point, the one caller that passes `{kind: 'dm'}`. A sibling predicate, `isAmbientIntakeListener`, runs immediately **before** this one on the ambient path (5.2a) — cheaper, and true for only one of the eight processes receiving a given channel message. It stays a sibling rather than a third arm here, since this function's `dm` arm must keep passing unconditionally for every persona.
- **Stage 1 classifier** — The cheap, per-message model call that scores whether an in-scope message describes work (`docs/VISION.md` §5.2) — numeric, not binary, so it can drive three-band routing rather than a yes/no gate. Scoring method and thresholds: `docs/decisions/STAGE-1-CLASSIFIER.md` (3.1) — one bundled structured-output call returning a single 0–100 confidence integer, on Claude Haiku 4.5 (no log-probs — the Claude API doesn't expose them on any model; no prefill either — it isn't used, and is confirmed dead only on other current models, not Haiku 4.5 itself). Built as `classifyMessageConfidence` (`packages/agents`, `zodOutputFormat` + `.messages.parse()`; 3.3); wired into every in-scope ambient channel/group message via `apps/server`, but only in the process of the designated ambient intake listener (`AMBIENT_INTAKE_PERSONA_ID`, Sarah per VISION §5.3) — the other seven drop an ambient message before any billed call (5.2a). A DM is classified by whichever persona was addressed, since Slack delivers it only to that persona's own app (3.7). A High-band score drives ticket-draft composition (**High-band auto-draft**, below; 3.4a-i); a Low-band score logs a real review-queue row **on an ambient message only** — a Low-band DM gets the ordinary conversational reply and no row (**Review queue**, below; 3.4c); a Mid-band score posts a real confirming question (**Confirming question (Mid-band)**, below; 3.4b-i). Gated by the same per-persona monthly cost cap as the DM chat-reply path (`checkCostCapAndAlert`, `haikuCostUsdMicros`, 2.6a/2.6b).
- **Confidence band** — The High/Mid/Low routing outcome derived from the Stage 1 classifier's numeric score (`docs/VISION.md` §5.2) — High ≥ 70 auto-drafts a reversible ticket, Mid (35–69) asks a confirming question, Low (< 35) logs silently to the review queue on an ambient message, and on a DM falls through to the ordinary conversational reply with no review-queue row (3.7). Thresholds calibrated against a live eval, not chosen from theory (3.1). Built as `classifyConfidenceBand` (`packages/core`, a pure `number → ConfidenceBand` function; 3.4a-i) — all three bands are wired to real actions (**High-band auto-draft**, **Confirming question (Mid-band)**, and **Review queue**, below).
- **High-band auto-draft** — The action a High-band confidence score triggers (`docs/VISION.md` §5.2) — an LLM composes a link-only ticket draft (title + body, no invented detail beyond the source message) from the classified message. Built as `composeTicketDraft` (`packages/agents`, Claude Sonnet 5, `zodOutputFormat` + `.messages.parse()`; 3.4a-i), wired into `handleAmbientChannelMessage` (`apps/server`). Gated by the **Situational-appropriateness gate** (below) in front of composition; a `pending_ticket_drafts` row is claimed keyed on the source message's own `ts` before anything is posted (5.2b), then the draft is posted as a real Slack message (`postMessage`) — in-thread on the source message for an ambient draft, top-level for a DM-triggered one (3.7) — the posted message's `ts` is recorded on that row (what a reaction is looked up by), and the 📦/🔁/✅ reaction legend (park to Backlog / redo / commit as a ticket) is seeded with real `reactions.add` calls (`addReaction`, `packages/slack`). On the **ambient** path, respects the 2.7a operating-rhythm guard (`evaluateOperatingRhythm`) — off-hours the draft is not composed at all; the message is instead preserved as a `'high-band-off-hours'` `review_queue` row (its Mid-band sibling writes `'mid-band-off-hours'`), rather than dropped. A mid-turn cost-cap halt writes `'high-band-cost-cap'`, and the **Situational-appropriateness gate** failing CLOSED on an infrastructure blip (not a genuine `appropriate: false` verdict, which stays silent by design — Alex, 2026-07-28) writes `'high-band-appropriateness-check-failed'`. A **DM-triggered** draft (3.7) deliberately does not consult the operating-rhythm guard: a draft composed because someone sent a DM is reactive, not Moe acting unprompted, so §14's rest rule no more reaches it than it reaches the DM reply it replaces — the cost cap still applies on both paths. Gated by its own fresh per-persona cost-cap check and `sonnetCostUsdMicros` accounting, same mechanism as every other real, billed call site in this cascade. Its cost-cap/operating-rhythm guard and the **Situational-appropriateness gate** below are both in shared `standing-proactive-guards.ts`, since the Mid-band confirming question needs the exact same two checks.
- **Confirming question (Mid-band)** — The action a Mid-band confidence score triggers (`docs/VISION.md` §5.2) — a short confirming question: a persona-voiced lead-in composed by `composeConfirmingQuestionLeadIn` (`packages/agents`, the persona's model via `resolvePersonaModel`; 5.3a-ii), followed by a fixed, code-controlled trailer naming the 👍/👎 mechanic, so the reaction affordance can't drift with the model's phrasing. On any composition failure, including a cost-cap halt, a fixed fallback lead-in is used instead. Ask-side built as `composeAndPostConfirmingQuestion` (`apps/server`; 3.4b-i): gated by the same cost-cap+operating-rhythm guard (`evaluateCostAndRhythmGuard`) and **Situational-appropriateness gate** the **High-band auto-draft** uses (shared `standing-proactive-guards.ts`). When that guard blocks an **ambient** question outside the operating-rhythm window it writes a `'mid-band-off-hours'` **Review queue** row rather than dropping the message, exactly as its High-band sibling writes `'high-band-off-hours'`; a mid-turn cost-cap halt writes `'mid-band-cost-cap'`, and the **Situational-appropriateness gate** failing CLOSED on an infrastructure blip (not a genuine `appropriate: false` verdict, which stays silent by design — Alex, 2026-07-28) writes `'mid-band-appropriateness-check-failed'`. Otherwise it claims a `pending_confirming_questions` row keyed on the source message's own `ts` (5.2b; `packages/core`, workflow-object shape with a `resolvedAt`/CAS claim, same as `pending_ticket_drafts` — not `review_queue`'s append-only shape, since a question genuinely resolves once), posts the question — in-thread on the source message for an ambient one, top-level for a DM (the surface is persisted on the row as `sourceSurface`, so the 👍 outcome can match it; 3.7) — records the posted message's `ts` on that row, and seeds a 👍 (yes, draft it) / 👎 (no) reaction legend — distinct from the High-band 📦/🔁/✅ legend, though not tell-apart-by-reaction-name-alone: 👍 is also Brief approval's own reaction (6.1d), and Plan approval's own reaction too (6.1e; VISION §6.3: "👍 on a brief or plan = approval"), reusing the same emoji for both rather than adding a new one each time, disambiguated by content instead — `dispatchConfirmingQuestionOutcome`'s own lookup always runs first, and only once it finds no matching confirming question does `handleReactionAdded` try a `ticket_briefs` lookup (`dispatchBriefApproval`), and only once _that_ also finds no match does it try a `ticket_plans` lookup (`dispatchPlanApproval`) as a further fallback — each later link gated to a `classifyConfirmingQuestionOutcome` result of `'yes'` specifically (a real 👍's `no`-equivalent, `-1`/`thumbsdown`, has no Brief- or Plan-approval equivalent and never falls through past the confirming-question check) and to Alex's own Slack user id (`ALEX_SLACK_USER_ID`, `packages/core/src/channel-scoping/alex-slack-user-id.ts`) so no other reactor's 👍 triggers a DB lookup beyond the confirming-question one. `dispatchConfirmingQuestionOutcome` and `dispatchBriefApproval` share the identical `Promise<boolean>` fallthrough contract (`true` = definitively matched, don't try the next link; `false` = try the next one); `dispatchPlanApproval` stays `Promise<void>`, since it's the chain's own terminal link and nothing currently follows it. No generalized, list-driven dispatch abstraction was built for this (considered and declined at 6.1e, Alex confirmed) — Plan→Build is the _last_ forward-approval reaction-triggered stage transition in the whole lifecycle, so there's no third occurrence of this pattern to justify one. `classifyConfirmingQuestionOutcome`'s `Map` (`packages/slack`) accepts both `+1`/`-1` (the names a real human click actually produces) and `thumbsup`/`thumbsdown` (kept as harmless accepted aliases). The answer-side (`handleReactionAdded`'s dispatch, `apps/server`; 3.4b-ii) classifies a reaction against both legends in order (`classifyReactionOutcome` first, then `classifyConfirmingQuestionOutcome`) and dispatches to `dispatchConfirmingQuestionOutcome`, mirroring the pre-existing draft-outcome dispatch's own lookup → null-check → resolved-check → outcome-switch shape. 👍 (`draftFromConfirmingQuestion`) checks the cost cap _before_ claiming the question — a halted persona leaves it unresolved for a later retry — then reuses the **High-band auto-draft**'s own `postAndPersistDraft` directly (not reimplemented; that function's params were narrowed to a minimal structural type so a reaction-outcome context, which has no `channelType`/`userId` to build a full inbound message with, could call it). 👎 (`logConfirmingQuestionAsNo`) logs to **Review queue** with `outcomeReason: 'mid-no'`. Silence/no-response detection is chunk 3.5's own write (`outcomeReason: 'mid-silence'`, see **Review-queue sweep**, below) — a manually-triggered sweep, since the codebase had no scheduled-job infrastructure at 3.5. If 👍's own downstream draft composition/posting/persistence fails after the claim already won, the **Claim-then-act fallback fix** (below) logs a `'mid-yes-failed'` **Review queue** row instead of leaving the question's own context lost.
- **Review queue** — The action a Low-band confidence score triggers on an **ambient** message (`docs/VISION.md` §5.2's "nothing is silently eaten" backstop; a Low-band DM writes no row — it gets a real conversational reply instead, chunk 3.7) — a plain append-only log row, not a workflow object (no resolved/claimed state, unlike **Reaction-gate outcomes**' `pending_ticket_drafts`, below). Built as a `review_queue` table + `createReviewQueueEntry` (`packages/core`; 3.4c), wired into `handleAmbientChannelMessage`'s Low-band branch (`apps/server`, `logAmbientIntakeToReviewQueue`) — captures the source message text plus the Stage 1 classifier's own confidence/reasoning. `outcomeReason` is one of 13 values (`reviewQueueEntrySchema`, `packages/core/src/intake/review-queue-entry.ts`): `'low-confidence'` (3.4c, the only happy-path writer); `'mid-no'` (3.4b-ii, see **Confirming question (Mid-band)**, above); `'mid-silence'` (3.5, see **Review-queue sweep**, below); `'mid-yes-failed'` (the **Claim-then-act fallback fix**'s own write, below); `'high-band-off-hours'`/`'mid-band-off-hours'` (3.9, an ambient High- or Mid-band message the operating-rhythm guard blocked); `'high-band-cost-cap'`/`'mid-band-cost-cap'` (3.10, a cost-cap halt inside `evaluateCostAndRhythmGuard`, mid-turn after the classifier output already exists); `'high-band-appropriateness-check-failed'`/`'mid-band-appropriateness-check-failed'` (3.10, the **Situational-appropriateness gate** failing CLOSED on an infrastructure blip, not a genuine `appropriate: false` verdict, which stays silent by design — Alex, 2026-07-28); `'classification-failed'` (3.11, the Stage 1 classifier call itself erroring inside `classifyMessageForIntake`, before any band is determined, so it is the only value tied to no band — `confidence` is nullable only for this value, Alex, 2026-07-29, enforced by `reviewQueueEntrySchema`'s own cross-field `.refine`); `'high-band-repeated-sender'`/`'mid-band-repeated-sender'` (5.3a, `evaluateSenderFrequencyGuard` blocking a second High/Mid-band trigger from the same sender in the same channel within a 15-minute cooldown window). The Low band is the only happy-path writer; the other twelve record something that did not go as intended. Chunk 3.5's own `review-queue-sweep` script is this table's real, live consumer.
- **Review-queue sweep** — BUILD_PLAN 3.5's own reader for **Review queue** (above) — VISION §5.2's "nothing is silently eaten" backstop, given a human-facing surface. Triggered manually (Alex confirmed): a CLI script, `apps/server/scripts/review-queue-sweep.ts` — not a background timer, since the codebase had no scheduled-job infrastructure at 3.5 (7.2a's own future ceremony scheduler is the real home for that). `runReviewQueueSweep` (`apps/server/src/review-queue-sweep.ts`) is the fully DI-testable core: resolves any confirming question unresolved past a 24-hour threshold as `'mid-silence'` (atomically re-claiming it and logging the `review_queue` row in one transaction — the **Claim-then-act fallback fix**, below — so whichever claims the question first wins: a real 👍/👎 answer that claimed it first is never overwritten as silence, and a reaction arriving after the sweep's claim is ignored), lists the `review_queue` rows created since the persona's last completed sweep (`packages/core`'s `sweep_state` table + `sweep-state-repository.ts`, a persona-scoped timestamp marking the upper bound of the last completed sweep's window, not a fixed rolling window, so a skipped or irregularly-run sweep picks up where the last completed one left off — Alex confirmed that design; the exceptions `runReviewQueueSweep`'s own TSDoc names still apply), and DMs Alex (`MOE_COST_ALERT_SLACK_USER_ID`, the same audience the cost-cap alert ladder already uses) a formatted digest grouped by `outcomeReason` (Alex confirmed) — thirteen sections, one per **Review queue** value above. `formatSweepMessage`'s section order derives from `SECTION_LABEL_BY_OUTCOME_REASON`'s own keys rather than a second hardcoded list, so a new `outcomeReason` value can't type-check into one list and silently vanish from the other. Skipped entirely when there's nothing new. `sweep_state` only updates once _both_ listing and — when there's real content to report — the digest post itself succeed, so a listing failure or a failed Slack post each leave the window untouched rather than silently skipping past rows Alex was never shown.
- **Claim-then-act fallback fix** — A cross-cutting fix (PR #51) for a structural gap in `apps/server`: four functions each atomically claim a row (`resolvePendingTicketDraft`/`resolvePendingConfirmingQuestion`'s own CAS), then perform a second action that can fail, permanently burning the claim with nothing to show for it — the exact "nothing is silently eaten" failure VISION §5.2 exists to prevent. `commitAsTicket` (backing the ✅/📦 outcomes) and `logConfirmingQuestionAsNo`/`logStaleQuestionsAsSilent` (👎, and the sweep) do a second **pure DB write** with nothing external in between — `@moe/core`'s `createTicketFromDraft`/`resolveConfirmingQuestionAndLog` close these three completely, wrapping claim + write in one Kysely transaction: a downstream-write failure rolls the claim back too, leaving the row available for a future retry. `draftFromConfirmingQuestion` (👍) can't use the same fix — Anthropic/Slack calls sit between the claim and the final DB write, and a DB transaction can neither hold open across two slow external calls nor undo an already-sent Slack message — so it keeps its own explicit claim and instead logs a **Review queue** fallback row (`outcomeReason: 'mid-yes-failed'`) when `postAndPersistDraft` fails downstream, a documented narrower residual gap (the fallback write can itself fail) rather than a full close.
- **Situational-appropriateness gate** — The check VISION §9 requires before any standing-proactive action, named after the Viktor incident (a competitor bot reacting to a layoff announcement with a skull emoji, `docs/decisions/CAST-ROSTER.md` and VISION §9) — a system that can act without being asked can act at the wrong moment. Built minimally as `evaluateSituationalAppropriateness` (`packages/agents`, Claude Haiku 4.5, `zodOutputFormat` + `.messages.parse()`, returning `{appropriate: boolean, reasoning: string}`; 3.4a-iii): an LLM content classifier over the source message text, checking for a serious/sensitive human situation (layoffs, death, crisis, grief, conflict) versus ordinary work chat, not a keyword list or external toggle (Alex confirmed). **Fails CLOSED** on any gate failure (an API error, not just `appropriate: false`) — the opposite of `checkCostCapAndAlert`'s fail-open design, since an uncertain safety signal should block the risky action, same "better to wrongly rest once" reasoning as 2.7a's bank-holiday guard. Gates the **ambient** High-band auto-draft and Mid-band confirming question only — not the reaction-outcome dispatch below, and not a DM-triggered draft or question (3.7), both of which respond to a human action rather than posting unprompted (Alex confirmed: a human's own reaction is a response to the bot, not the bot acting unprompted, same distinction 2.7a's core-hours guard already draws for DM replies). 8.5's full version extends it to every standing-proactive surface; only these two ambient surfaces are wired so far (the High-band draft at 3.4a-iii, the Mid-band question at 3.4b-i). `apps/server`'s own wrapper is `evaluateSituationalAppropriatenessGuard` (`standing-proactive-guards.ts`), returning a `{satisfied, reason}` decision so an **ambient** caller can tell the gate's two `false` reasons apart: an infrastructure blip (`'evaluation-failed'`) writes a **Review queue** row (`'high-band-appropriateness-check-failed'`/`'mid-band-appropriateness-check-failed'`), while a genuine `appropriate: false` verdict (`'inappropriate'`) stays silent — Alex, 2026-07-28, that the latter is a considered decision, not silent data loss.
- **Reaction-gate outcomes** — The three deterministic actions the 📦/🔁/✅ reaction legend maps to (`docs/VISION.md` §5.4's trust-erosion rule: routing decisions with real consequences stay off the LLM layer, not just the drafting step). Built at 3.4a-ii: `classifyReactionOutcome` (`packages/slack`, a pure Slack-reaction-short-name → outcome mapping verified against the real `iamcal/emoji-data` database: ✅ is `white_check_mark`, 🔁 is `repeat`, 📦 is `package`), a `pending_ticket_drafts` table + repository (`packages/core`, the "parent-message state" tracking which draft a Slack message's reactions belong to — `resolvePendingTicketDraft`'s atomic claim, same CAS shape as chunk 1.3's `claimTicket`, guards against a reaction double-firing the same outcome twice), and three outcome-path functions (`apps/server`'s `reaction-outcome-actions.ts`): ✅ commits the draft as a real `Brief` ticket, 📦 parks it to an untriaged `Backlog` ticket (both `projectKey: 'chief-clancy'`, VISION §3.4's single-project scope; `severity: 'Medium'`, a fixed placeholder (Alex confirmed) until a real triage signal exists), and 🔁 recomposes a fresh draft from the _original_ source message via `composeTicketDraft` (its own fresh cost-cap check and `sonnetCostUsdMicros` accounting) and updates the pending draft in place, leaving it open for a further reaction. Wired to a real Socket Mode `reaction_added` listener (3.4a-iii, `createSocketModeListener`'s `onReactionAdded` opt, dispatching to `handleReactionAdded` via `createReactionHandler`) — the self-authored-reaction filter is closed in `@moe/slack`'s `handleSocketModeReactionEvent`: it compares the event's `user` against a `botUserId` fetched once at startup (`fetchBotUserId`, a thin wrapper over `auth.test`) and never dispatches a self-authored reaction, so `handleReactionAdded` itself never needs to know about bot identity.
- **Draft-outcome tracking** — BUILD_PLAN 3.6's own counting layer over **Reaction-gate outcomes** (above) — VISION §5.4's named production metric for the whole intake cascade ("the rate of ignored/rejected drafts, not an academic precision score"). The real outcome space is four-way (✅/📦/🔁/no reaction), and 🔁 isn't terminal — a redone draft can still later be ✅/📦'd. Bucket definitions (Alex confirmed): `'committed'` folds in both ✅ and 📦 (both mean "accepted as real work"); `'redone'` means still-open **and** regenerated at least once (no age qualifier — a redo is itself an explicit human action); `'ignored'` requires never-redone **and** older than a 24-hour threshold (reusing **Review-queue sweep**'s own silence-threshold reasoning) — a still-open, never-redone, too-young draft falls into none of the three buckets. Counts are lifetime-cumulative, not windowed like `review_queue`'s own entries — VISION §5.4 names the ignored/rejected-draft rate as the metric to watch, favoring the full accumulated trend over a noisy per-window slice. Built as a `redo_count` column on `pending_ticket_drafts` (`Generated<number>`, excluded from `pendingTicketDraftSchema`'s own pure domain shape — same reasoning `ticketSchema` excludes `version`/`claimedBy`), incremented inside `updatePendingTicketDraftContent`'s existing UPDATE, and `getDraftOutcomeCounts` (`packages/core`'s `intake/draft-outcome-counts.ts`), a single aggregate query using Postgres `FILTER (WHERE ...)` clauses rather than three round-trips. Surfaced as a `📊 Draft outcomes (all time): N committed, M redone (open), K ignored — R% acceptance rate` line in the **Review-queue sweep**'s own digest (rate computed over `committed`/`ignored` only, excluding still-open `redone` drafts) — riding along with an existing digest post rather than triggering one, since a lifetime-cumulative count is almost never zero, so triggering on it would defeat the sweep's quiet-when-nothing-new behaviour. Scoped to `origin: 'high-band'` only — `pending_ticket_drafts` is a shared table for ambient High-band auto-drafts, Mid-band 👍-confirmed drafts and, since 3.7, DM High-band drafts, and counting them together skewed the reported rate upward; an `origin` column distinguishes them.

## GitHub & the board (BUILD_PLAN Stage 4)

- **Board home** — **Resolved** at 4.3 (`docs/decisions/BOARD-AND-CAPACITY-MODEL.md`): moe's own DB (`packages/core`'s `tickets` table, load-bearing since chunk 1.2b) is the canonical board — GitHub issues are an external mirror (**GitHub issue discovery**'s triage queue below; **Outbound issue creation** below creates/links GitHub issues _from_ tickets, chunk 4.4b), not the board itself. GitHub Projects v2, cited as "old VISION's answer" in BUILD_PLAN's own original framing, was never built and isn't adopted.
- **External-post attribution** — VISION §6.7's three-layer AI-transparency requirement (bot identity / persona attribution in the message body / a footer escape-hatch to Alex) for every externally-visible artifact moe writes — GitHub issues now, PRs and review comments at Stage 6. Resolved at 4.4a (Alex confirmed): the platform-layer bot identity is the single shared GitHub App already built at chunk 4.1 (no per-persona GitHub identity, unlike VISION §6.6's Slack reversal); the persona roster's `displayName`/`role` mapping needed by both `packages/agents` and `packages/github` (which cannot import each other, `docs/CONVENTIONS.md` §Architecture Enforcement) lives in `packages/core/src/persona-roster.ts` (`PERSONA_ROSTER`, `personaIdSchema`); and the footer escape-hatch is a direct `@Pushedskydiver` GitHub mention rather than a Slack link or email, since the reader is already on GitHub and may have no Slack access. Built as `composeExternalPostBody` (`packages/github`) — a pure, deterministic-boilerplate formatter (no LLM call) appending an attribution line and the footer to any given post body. First real consumer: **Outbound issue creation** below (4.4b), wired into every created GitHub issue's body.
- **GitHub issue discovery** — BUILD_PLAN 4.2's own polling layer — finds every open issue in the single repo `packages/github`'s `GithubConfig.repo` names (`MOE_GITHUB_REPO`, `"owner/name"`) and upserts each into a `github_issue_triage` table (`packages/core`), the first real consumer of chunk 4.1's `createGithubClient`. Built as `listOpenIssues` (`packages/github`, Octokit's own `paginate` over `issues.listForRepo` — GitHub's Issues REST API returns pull requests too, so every response is filtered on the presence of a `pull_request` key before being normalized) and `discoverGithubIssues` (`apps/server`, DI-testable, mirroring **Review-queue sweep**'s own shape). Deliberately minimal — a pointer (issue number, title, URL, state, GitHub's own `updated_at`), not the full issue body (Alex confirmed), since a persona acting on an entry later (Brief-stage handler, 6.1b) fetches the current body fresh rather than risking a stale cached copy. `(repoOwner, repoName, issueNumber)` is the table's own natural composite primary key (no surrogate `id`) — a re-poll upserts the existing row in place (`ON CONFLICT ... DO UPDATE`, threading GitHub's own `updated_at` through) rather than inserting a duplicate or silently skipping. Triggered manually (`apps/server/scripts/discover-github-issues.ts`, `pnpm --filter @moe/server discover:github-issues`; Alex confirmed) — same no-scheduled-job-infrastructure precedent **Review-queue sweep**'s own TSDoc gives. The triage table's real reader is 6.1b: Sarah's pull loop runs a generic `preTickStep` once per in-hours tick (`apps/server/src/convert-next-triage-entry.ts`) that finds the single oldest still-unconverted, open entry (`findNextUnconvertedGithubIssueTriageEntry`, `packages/core` — an anti-join against `ticket_github_issue_links` on the natural `(repoOwner, repoName, issueNumber)` key) and converts it into a new `Brief`-status board ticket, atomically and crash-safely (`createTicketFromTriageEntry`, one transaction), bounded to at most one conversion per tick.
- **Outbound issue creation** — BUILD_PLAN 4.2's inverse — the plan's first GitHub _write_ (4.4b): creates a real GitHub issue for a chat-born ticket and persists the link, per **Board home**'s own decision that moe's DB stays canonical. A manually-triggered CLI script (`apps/server/scripts/create-github-issues.ts`, `pnpm --filter @moe/server create:github-issues`; Alex confirmed), same no-scheduled-job-infrastructure precedent **GitHub issue discovery**/**Review-queue sweep** already established, scanning every ticket without a linked issue; the ticket↔issue link lives in a `ticket_github_issue_links` table (`packages/core`), a separate table rather than columns on `tickets` itself, keeping **Board home**'s "GitHub issues are an external mirror" framing out of the pure domain schema. A claim-first idempotency guard inserts a `pending` row — `ticketId` primary key, `issueNumber`/`issueUrl`/`resolvedAt` all `NULL` — _before_ ever calling GitHub's `issues.create` (`createGithubIssue`, `packages/github`, schema-validated response per `docs/CONVENTIONS.md`'s External API Integration Patterns), so a process crash between a successful creation and the follow-up DB write can't trigger a duplicate issue on retry: a future run finds the claim already exists (`listTicketsWithoutGithubIssueLink`'s own `LEFT JOIN`) and skips the ticket. A claim still `pending` at a run's _start_ is necessarily left over from an earlier crashed run — surfaced via `listStuckPendingTicketGithubIssueLinks` for manual reconciliation, deliberately never auto-retried, since this codebase can't tell whether that prior claim's GitHub call actually succeeded without querying GitHub directly. Wires **External-post attribution**'s `composeExternalPostBody` into every created issue's body (persona hardcoded to Sarah). The App needs "Issues: Read and write".
- **Reconciliation poll** — BUILD_PLAN 4.4c — closes the loop **Outbound issue creation** opened: checks every resolved ticket↔GitHub-issue link's current GitHub state and reflects an external closure as `Cancelled` on the linked ticket. Any closure maps to `Cancelled` regardless of GitHub's `state_reason` ('completed' vs. 'not_planned') — nothing in moe closes issues via its own workflow today, so every closure this poll sees is genuinely external (Alex confirmed); a `Done` ticket is skipped outright (no GitHub call at all), the safeguard against a future closes-on-merge feature misreading a legitimate completion as an external cancellation; a reopened issue leaves an already-`Cancelled` ticket cancelled — VISION §3.1 calls `Cancelled` "a non-flow terminal state," so this poll never auto-reverses it, only logs a `warn` for a human to manually re-triage into a fresh ticket (Alex confirmed); and closure still cancels a ticket already in `Build`/`Review` (real work potentially in progress) rather than holding off, logged at `warn` instead of `info` so it's noticed rather than silently folded into the routine case (Alex confirmed). Built as `getGithubIssueState` (`packages/github`) — a per-issue `issues.get` lookup, not **GitHub issue discovery**'s own bulk `listOpenIssues`, since reconciliation already knows exactly which issue numbers to check and needs each one's precise current state, including a reopened one, which a bulk open-issues diff can't distinguish from "never closed"; `listResolvedTicketGithubIssueLinks` (`packages/core`, the inverse scope of **Outbound issue creation**'s own `listStuckPendingTicketGithubIssueLinks`); and `reconcileGithubIssues` (`apps/server`), triggered manually (`apps/server/scripts/reconcile-github-issues.ts`, `pnpm --filter @moe/server reconcile:github-issues`) — same no-scheduled-job-infrastructure precedent every Stage 4 poll has used. Purely an internal DB status change with no external post, so **External-post attribution**'s composer has no call site here. The closure→`Cancelled` path itself is thoroughly unit-tested but not live-verified against a real closed issue, since deliberately closing the real, still-open `chief-clancy#489` would conflict with its own documented purpose as an intentionally-left-open live-verification artifact from chunk 4.4b.

## Review & process (`docs/DEVELOPMENT.md`, `docs/DA-REVIEW.md`)

- **Chunk** — A single unit of `BUILD_PLAN.md` work — roughly one PR, one sitting, one reviewable idea, per `BUILD_PLAN.md`'s own sizing-discipline note.
- **Stage** — A group of chunks in `BUILD_PLAN.md` ending in something observable working end-to-end.
- **[GATE] chunk** — A chunk that needs an Alex conversation before it can proceed — flagged explicitly in `BUILD_PLAN.md`, never guessed past.
- **DA review** — Devil's-advocate review, dispatched from a fresh context, checked against `docs/DA-REVIEW.md` + `docs/CONVENTIONS.md` + `docs/RATIONALIZATIONS.md` + `docs/REVIEW-PATTERNS.md`.
- **spec-grill** — Two-phase adversarial review of a spec/plan/rationale doc before code moves, per `docs/DEVELOPMENT.md` §Two-phase grill discipline.
- **copilot-surrogate** — Factual-claim reviewer, mandatory on `fix(docs)` commits and on any PR touching a blast-radius doc, exceeding 50 LOC, or making a factual claim about the rest of the repo or an external library (`docs/decisions/REVIEW-GATE-DISCRETION.md`), reading each file in the PR diff, or in a Round-2 check the fix range's files, at HEAD (not diff-scoped).
- **Do-not-touch list** — Surfaces requiring Alex's explicit approval before editing (persona prompts, `docs/CEREMONIES.md`, `docs/VISION.md` §2/§14/§4.1, `docs/PERSONAS.md`'s roster table) — `AGENTS.md` §Non-obvious constraints.
- **NOTICED BUT NOT TOUCHING** — The self-review discipline of listing an out-of-scope improvement rather than fixing it inline (`docs/SELF-REVIEW.md`).
- **Blast-radius doc** — A policy-tier doc requiring Alex's merge (not self-merge), listed in `docs/GIT.md`. This doc, `ARCHITECTURE.md`, and `decisions/` are deliberately NOT on that list.
- **ADR** — Architecture Decision Record — the general industry term for a short, dated record of an architectural choice and its rationale. Moe's equivalent shape lives in `docs/decisions/`.
- **Persona-replay test** — A committed-fixture regression test (`packages/agents/src/personas/<id>/replay/persona-replay.test.ts`) that verifies a previously-recorded real-model transcript is still valid against the persona's _current_ `prompt.md` — no network call, CI-blocking. `docs/decisions/PERSONA-REPLAY-HARNESS.md` (5.4).
- **Replay fixture** — A committed JSON file (`.../replay/fixtures/<scenario-id>.json`) capturing one real Anthropic API call's full outcome — the cascade function's own `Result`, plus `stop_reason`/raw output tokens, content-hashes of the prompt and scenario input, and the resolved model id used to record it. Written only by `record-persona-replay.ts`.
- **Replay recording** — The manual, live step (`pnpm --filter @moe/agents record:replay -- <personaId>`) that (re)writes a persona's replay fixtures against the real API — required after any `prompt.md` edit, reviewed alongside the prompt change in the same PR.

## Tools & general terms

- **HITL** — Human-in-the-loop — a step requiring human judgment before proceeding.
- **MCP** — Model Context Protocol — an open standard, originated and open-sourced by Anthropic, for connecting AI applications to external tools/systems. Per-persona tool allowlists and the CLI-vs-MCP decision rule are settled at 6.0 (`docs/decisions/TOOL-ALLOWLIST-GRID.md`, resolving `docs/VISION.md` §11's own deferral).
- **Four-eyes principle** — The general security/engineering practice of requiring two people (or an agent plus a human, or two independent agents) to approve a sensitive action before it takes effect.
