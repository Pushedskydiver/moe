# Stage-1 Classifier — Scoring Method & Thresholds

## Decision

Closes VISION §5.2's open question with two discrete calls: **scoring method** is a single bundled structured-output call returning one integer confidence score 0–100 (no separate scoring call, no log-probs, no prefill), on **Claude Haiku 4.5**; and **thresholds** are **High ≥ 70, Mid 35–69, Low < 35**. Grounded in a live 24-message eval against the real Claude API (BUILD_PLAN chunk 3.1's own "small offline eval set of real-ish messages" requirement), not decided from theory alone.

## Context

VISION §5.2 named three candidate scoring methods without picking one — "model-reported probability vs. a separate scoring call vs. log-probs" — and left the High/Mid/Low thresholds unset, both explicitly blocking §5's implementation. Checked against the actual Claude API (verified via both the `claude-api` skill's bundled reference and a live fetch of the current Anthropic docs, not assumed from memory), one of the three named candidates turns out not to be a real option at all, and a related technique it's sometimes paired with — prefill, not itself one of VISION's three candidates — doesn't offer a workaround either:

- **Log-probs don't exist, on any model.** The Anthropic Messages API has never exposed token-level log-probabilities, unlike OpenAI's API — nothing in the current API surface (structured outputs, streaming, tool use) offers a log-prob field, on Haiku 4.5 or any other model. This alone rules out "log-probs" as a scoring method regardless of anything else.
- **Prefill's own restriction doesn't reach the model this ADR actually adopts.** Assistant-turn prefill (the classic pairing with log-probs-style scoring elsewhere) is confirmed, via a live fetch of the current migration guide, to return a 400 on Opus 4.6/4.7/4.8, Sonnet 4.6/5, and Fable 5/Mythos 5 — but Claude Haiku 4.5, the model Decision 2 below adopts, is not mentioned anywhere in current documentation (live or bundled) in relation to prefill. Its conspicuous absence from every one of these enumerations suggests it isn't restricted there, but that's an inference from omission, not a positive confirmation — stated honestly as such rather than asserted either way. It doesn't change this decision regardless: log-probs' total absence already rules out any prefill-paired log-prob technique on every model, Haiku included — prefill support alone, without log-probs to pair it with, isn't a substitute for any of the scoring methods VISION §5.2 actually named.

That leaves "model-reported probability" and "a separate scoring call" as the only real candidates — and they turn out to be the same underlying mechanism (ask the model to state a number) at two different points in the pipeline: bundled into the classification call itself, or split into a dedicated second call. Alex confirmed the bundled approach via `AskUserQuestion` before the eval ran, matching VISION §5.2's own "a fast, cheap model call" framing for Stage 1 — a second call doubles latency and cost per message for no accuracy benefit this eval identified.

## Method

Real Claude API calls (not simulated), one classification call per message, using `output_config: {format: {type: "json_schema", schema}}` (structured outputs — a real API feature, not a workaround) requiring `{confidence: integer, reasoning: string}`. System prompt: _"decide which messages describe actual work that needs doing... versus general conversation, social chat, or commentary that doesn't need any action."_

**24-message synthetic eval set** (Alex confirmed synthetic over sourcing real historical messages, via `AskUserQuestion`) — 8 clear work requests, 8 clear banter/social messages, 8 deliberately ambiguous/borderline messages (a mix of soft-pedaled bug reports, discussion questions, and genuinely non-actionable but work-adjacent chatter) — run against **both Claude Haiku 4.5 and Claude Sonnet 5** for a real cost/accuracy comparison, not an assumed one.

## Decisions

1. **Scoring method: one bundled structured-output call, single 0–100 integer.** Matches VISION §5.2's "one score in, three bands out" literally — the model's only output is the number (plus a `reasoning` string for debuggability, not itself part of the routing decision). Of VISION's three named candidates, log-probs is ruled out outright (see Context above — the Messages API doesn't expose it, on any model); "model-reported probability" and "a separate scoring call" turn out to be the same mechanism at two different points in the pipeline, and this decision picks the bundled form of that mechanism over splitting it into two calls (see Context's cost/latency reasoning). Prefill — not one of VISION's three named candidates, but a related technique sometimes paired with log-probs-style scoring elsewhere — doesn't offer a usable workaround either, for the reason given in Context.

2. **Model: Claude Haiku 4.5.** Real eval data, not a guess. Two clusters, kept explicitly separate: Haiku's 8 pure **work**-category messages scored **85–95**; the 4 **ambiguous** messages that turned out to describe a real, actionable issue ("footer links look broken," "keep getting logged out," "slow dashboard loads today," "do we have a billing docs") scored **72–85**. Combined, every message carrying a genuine work signal scored ≥ 72, and every banter or genuinely-non-actionable message scored ≤ 35 (see Decision 3 for the one exception at exactly 35) — a 36-point band (scores 36–71) with zero messages in it either way. Sonnet 5 showed a messier spread on the identical 24 messages: its own "coffee machine" outlier landed at 55, squarely inside its ambiguous cluster, and its pure work-category floor was lower too (78 vs Haiku's 85). Haiku is also ~2–3× cheaper per token (confirmed against current pricing: $1/$5 per MTok flat vs. Sonnet 5's $2/$10 through 2026-08-31, then $3/$15) — for a gate VISION §5.2 explicitly wants "fast, cheap" and that runs on every in-scope message, not just addressed ones, the cheaper model winning on the actual eval data (not just cost) makes this an easy call. Rejected: Sonnet 5 (moe's already-adopted chat-turn model, VISION §11) — no accuracy advantage observed on this eval to justify the extra cost for a high-volume gate.

3. **Thresholds: High ≥ 70, Mid 35–69, Low < 35.** The High floor (70) sits with two points of real margin below the lowest genuine-signal score Haiku produced (72). The Low ceiling is deliberately a strict `< 35`, not `≤ 35`: Haiku's highest banter score — 35, "coffee machine is broken again" — therefore lands in **Mid**, not Low. That's a deliberate outcome, not a boundary slip: both models scored this message (labeled banter going in, Haiku 35 / Sonnet 55) meaningfully higher than every other banter message — arguably the _model_ being right and the label being the weaker ground truth (a broken coffee machine is a low-priority but real facilities complaint, not pure social chat), left unrelabeled since an eval that adjusts its own ground truth to agree with the system under test isn't measuring anything, and flagged as a concrete illustration of why VISION §5.2 rejected a binary yes/no gate: a numeric score captures exactly this kind of real, non-binary distinction a boolean would flatten. With that one message accounted for, no other Haiku score in this eval fell inside the Mid band at all — every remaining message was either a confident work signal (≥ 72) or confidently non-actionable (≤ 25). That means the Mid band's real-world population, beyond this one boundary case, is unverified by this specific eval — worth watching once real traffic exists (see Triggers below). Sonnet 5's own scores did land several messages inside the same 35–69 range (40, 55, 65, 68) — consistent with Decision 2's point that Sonnet's separation was messier, not a contradiction of this finding, which is scoped to the model actually being adopted.

## Deferred / explicitly rejected

- Per-persona or per-channel threshold tuning is out of scope here — VISION §5.2 doesn't ask for it, and this ADR's job is closing the blocking open question, not designing a tuning system BUILD_PLAN hasn't scoped.
- A larger, more statistically rigorous eval set (100+ messages, inter-rater labeling) was considered and rejected for this chunk — BUILD_PLAN 3.1 explicitly scopes this as "a small offline eval set," a spike to unblock implementation, not a permanent calibration benchmark. Real production traffic (chunk 3.3's classifier gate, run silently for a few days before 3.4a-i acts on it) is the mechanism BUILD_PLAN already names for larger-scale validation.

## Triggers for re-evaluation

- Once chunk 3.3's classifier gate runs against real production traffic (logged, not yet acted on, per BUILD_PLAN's own sequencing) and real messages start populating the Mid band beyond this eval's single boundary case (the coffee-machine message) — confirm the Mid-band behavior (a confirming question) reads sensibly against real examples, not just the synthetic eval's near-empty middle.
- If Haiku 4.5 is ever deprecated/retired or a materially cheaper/faster model ships, re-run this same 24-message eval (or an expanded version) before assuming the new model's score distribution matches these thresholds.
- If the ignored/rejected-draft rate VISION §5.4 names as the real production metric shows systematic miscalibration in either direction (drafts too often ignored → High threshold too low; real work silently dropped → Low threshold too high), revisit the specific threshold values, not the scoring method itself.
- **A category definition can produce a confidently correct score for the wrong reason** (added 2026-08-01, BUILD_PLAN 3.12 — see that addendum below). The three triggers above all assume the category boundary itself is right and only the threshold or the model's calibration against it needs adjusting. BUILD_PLAN 3.12 found a case where the _definition_ was ambiguous in a way that made every score along it defensible by the letter of the prompt — Haiku's own `reasoning` field read correctly, and the score was high-confidence, not borderline. Watch for that combination specifically (a confident score whose stated reasoning is locally correct but misses an intended distinction the category text never actually drew) — it doesn't look like a miscalibration and won't surface through the ignored/rejected-draft rate the same way a threshold problem would, since the model isn't uncertain.

## Addendum (2026-07-25, BUILD_PLAN 3.7): the prompt now sees DMs, and is knowingly left as-is

Chunk 3.7 routed DMs through this classifier. Its system prompt still opens "You are a fast triage classifier for a shared team Slack channel", which is now inaccurate for half of what it scores.

**Decision (Alex, before the chunk merged): leave the prompt unchanged and observe first.** The thresholds recorded above — High ≥ 70, Mid 35–69, Low < 35 — were calibrated against a live 24-message eval run on this exact prompt text. Editing the prompt invalidates that calibration, and there is currently no evidence that the channel framing actually distorts DM scores; changing a calibrated prompt on a hunch trades a known-good configuration for an unmeasured one.

**What would change the decision, and how it would show up.** VISION §5.3 settles that a DM to a named persona is _already unambiguous_, which argues a DM should score at least as high as the equivalent channel message, not lower. So the failure mode to watch for is specific: work-shaped DMs landing in Mid (a confirming question for something plainly actionable) or Low (a chat reply where a draft was wanted). **Be precise about what can actually be observed, because the obvious instrument does not cover it.** Chunk 3.5's sweep digest is _not_ the instrument here: a Low-band DM deliberately writes no `review_queue` row at all (3.7's own design point), `review_queue` carries no surface axis of its own — its `channelId` still admits the same `D…` heuristic as the logs, but `formatSweepSection` renders only the source text and confidence, so a Mid-band 👎 or silence row is indistinguishable from an ambient one _in the digest_, and `getDraftOutcomeCounts` filters to `origin = 'high-band'`, which excludes DM drafts by design. Every symptom named above is therefore invisible in the digest.

What _does_ work today is lower-level and manual: the `classified inbound message` structured log records `channelId`, `messageText`, `confidence` and `reasoning` for every classification, and a DM is identifiable by its `D…` channel id — so a log search over real traffic shows the DM score distribution directly. `pending_ticket_drafts` can be queried on `origin = 'high-band-dm'` for the drafts that did fire. That is enough to answer the question from real data, but only by going and looking; nothing surfaces it unprompted.

If this needs to become routine rather than investigative, the cheap fix is a surface axis on `review_queue` plus a DM-scoped line in the sweep digest — filed against BUILD_PLAN 3.7's own deferred-metric note rather than done speculatively here.

If it does show up, the options in rough order of cost are: neutral wording that names neither surface (cheapest, still needs a re-run of the eval); or passing the surface as context so the classifier can score a DM as the more-directed surface §5.3 describes (most principled, largest change — new parameter, new prompt branch, full recalibration).

## Addendum (2026-08-01, BUILD_PLAN 3.12): a wrong category definition, not a wrong threshold

Found live within minutes of the first real DM to reach Sarah's real `prompt.md` (the 5.3a-ii fleet deploy, 2026-08-01 — see `PROGRESS.md`'s "Session 29 loading instructions"): Alex's `is the auth work finished?` scored 75 → High → auto-drafted a ticket whose entire body restated that a question had been asked. `CLASSIFIER_SYSTEM_PROMPT`'s category definition included "a question that needs someone to act," and Haiku applied it correctly — a status question genuinely is a question someone needs to answer. Nothing in the definition distinguished that from a request phrased as a question ("can someone look at the deploy?"), which does need a ticket.

**Settled with Alex before code moved:** a pure status question about already-known/tracked work routes to **Low band** (the ordinary conversational reply), not Mid — a confirming question there would ask "want me to open a ticket for this?", a non-sequitur when there's no ticket to confirm. Low is also where VISION §7.6's evidence-before-verdict discipline and the `report_status` tool already live (`packages/agents/src/status-claim-tool.ts`), which is exactly the behavior the test that found this bug was probing for.

**Two live-eval rounds against the real API, not reasoning about the prompt text alone** (this ADR's own original methodology, re-applied): a first attempt broadened the category clause to exclude any "status or informational question," which fixed every status-question case but also pulled "do we have a billing docs page anywhere" — this ADR's own Decision 2 ambiguous-cluster example, deliberately kept in as a real signal — from 60 (Mid) down to 15 (Low). (Decision 2 above recorded this exact message at 72–85 in the original 24-message eval; this addendum's own 60 doesn't reproduce that — the same gap already noted for the coffee-machine row below — this production prompt was freshly authored for this call site, not a verbatim copy of the original eval prompt — not a new discrepancy. What matters for this addendum's argument is the relative before/after movement against today's own old-prompt baseline, not matching 2026-07-18's absolute number.) That is a real regression, not a cosmetic one: the Low-band conversational reply has no ticket-creation tool, only `report_status`, so a message landing there has no path to becoming a tracked ticket at all, unlike Mid's confirming question. A second, narrower wording fixed the target cases without the regression — anchored specifically on "asking whether an already-identified piece of work is finished, done, or has happened yet," with an explicit carve-out preserving existence/resource-lookup questions:

The one deliberate, observed side effect beyond the target fix: the mixed conditional case shifted from High to Mid. Haiku's own reasoning flagged real ambiguity in a request that's contingent on an unconfirmed status ("wrap it up **if not** finished") — a confirming question is a defensible response to that uncertainty, arguably better than committing straight to a ticket. **Thresholds are unchanged — High ≥ 70, Mid 35-69, Low < 35 still hold.** This is a category-definition fix, not a recalibration: every score above stays within (or moves cleanly across, with real margin) the existing bands, so Decision 3's threshold values did not need to move.
