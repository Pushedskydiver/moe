**Major novel patterns Session 45:**

1. **MMM — A spec-grill's own evidence-gathering step needs test cases genuinely shaped to trigger the condition under test, not just a re-run of the existing suite.** Re-recording 63 replay scenarios never designed to be a plain acknowledgment couldn't tell "grounding doesn't cause reach-for-behavior" from "the suite never once asked the question" — a zero-usage result from that step would have been unfalsifiable in the direction that mattered. Any future "does the model reach for tool X" verification needs at least one scenario per persona shaped to genuinely trigger X, not an assumption that the existing suite already covers it.
2. **NNN — A domain-clause phrased as the persona's own verdict ("confirmed clean") rather than an incoming event ("a retest landing") collides with that same persona's pre-existing evidence-gating discipline.** Priya's original react-grounding wording read as her own "confirmed" claim, exactly the shape her `report_status` bullet exists to gate — caught in spec-grill before any file was touched, not after. Any future tool-grounding text for a persona whose prompt already has a "don't assert unverified claims" bullet should stay event-framed, not self-assertion-framed.
3. **OOO — Claiming a review finding was "folded"/fixed inside a build narrative is itself a claim needing the same verification discipline as any other status claim.** Two independent reviewers (`da-review`, a `copilot-surrogate` batch) caught this session's own authored `BUILD_PLAN.md` narrative asserting two fixes were folded at R1 when neither had actually landed in the diff — `docs/RATIONALIZATIONS.md`'s "I said I'd fix it, so it's fixed," this time in Claude's own prose, not code. "I noted this as a finding" and "I fixed this" are two different, independently-checkable claims — never conflate them in a narrative, and expect a review pass to check the narrative's own claims against the real diff, not just the code against the plan.
4. **PPP — A carried-forward "will resolve itself" explanation is a claim; give it a re-check date, and when the date passes, diagnose instead of waiting.** Sessions 44 and 45 both attributed Marcus not posting a Plan for "CLI hangs on large repos" to the core-hours guard (branch LLL). Checked 2026-09-27, 16 days and ~11 weekdays later: the ticket is still `Plan` with zero `ticket_plans` rows. **Real cause, from the code:** the ticket's `ticket_briefs` row predates migration `0026`, so `summary = ''` / `scope = []` (visible, and passed over, in Session 45's first DB query); `createPlanStageNeedsWorkCheck` returns false when `summary === ''`, so Marcus's pull loop never claims it — silently, with no log — and `handle-plan-stage-ticket.ts:126` would log an error and skip if it ever did. The pull loop itself runs (`main.ts` → `startPullLoop`, 60 s default). LLL's fact (the guard exempts a listener but not a work step) is still true, it just wasn't the cause here. When a stall outlasts its explained wait, inspect the item's whole row and read the gate that selects it before the schedule.
